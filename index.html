The data hasn't changed. The question hasn't either. But when reports keep separate copies of a calculation, one can get updated while another keeps the old rule.

With dbt, reports can build on calculations the team maintains and checks in one place.

Keep the rule shared.
Let the reports build on it.

Change how net sales is calculated, and every copy of that rule needs updating. Miss one, and someone has to explain why the reports no longer agree.

In dbt, the team can put that calculation in a model: a query that prepares data for other steps to use. Reports read from the shared results.

The team can add tests, explain the rules in documentation, and review changes in Git before using them in reporting.

What changes for the business?

Teams can write reusable SQL and tests without dbt. dbt brings that work into a project they can maintain as reporting grows.

Fewer copies to update

A change to a shared calculation has fewer places to maintain and check.

Problems caught by defined checks

Tests flag issues the team has chosen to check, such as duplicate orders or invalid discounts.

Less guesswork when numbers change

The team can see the calculation, the reports that depend on it, and what changed.

Start with one report that matters.

I'd start with an existing process where several reports repeat the same calculation.

The team still has to agree on the rules and choose useful tests. A small pilot gives you a way to see whether dbt makes that work easier.

  1. Agree on the rules. Decide what the metric means and which records count.
  2. Build and compare. Use a shared dbt model and check its results against the existing reports.
  3. See what improves. Does changing a rule take less work? Are the results easier to validate?

Use the pilot to decide where dbt belongs next.
